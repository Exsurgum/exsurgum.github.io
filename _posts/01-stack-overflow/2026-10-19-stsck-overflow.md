## 什么是栈溢出

本文中的“栈溢出”指的是**栈缓冲区溢出（Stack-based Buffer Overflow）**：程序向栈上的缓冲区写入数据时，超出了它的边界，导致缓冲区之外的内存被改写。

例如下面这个函数：

```c
#include <unistd.h>
void vuln(void)
{
    char buf[16];
    read(0, buf, 64);
}
```

`buf` 只能容纳 16 字节，但这次 `read` 调用请求从标准输入读取最多 64 字节。如果实际写入的数据超过 16 字节，就会越过 `buf` 的边界。

越界的数据可能覆盖相邻的局部变量、保存的栈帧信息，或者函数的返回地址。具体覆盖到什么，取决于程序实际的栈布局和写入长度。

这可能导致数据被篡改或程序崩溃。如果保存的返回地址能够被控制，并且满足相应的利用条件，还可能改变函数返回后的执行位置。

## 栈溢出的原理

沿用上面的例子，下面依次说明：输入怎样越过缓冲区边界、怎样影响保存的返回地址，以及返回地址被改写后怎样影响执行流程。

### 越界写入发生在哪里

`buf` 的 16 个元素连续存放在内存中，下标范围为 `0` 到 `15`。

假设本次 `read()` 实际读取并写入了 20 个 `A`，每个 `A` 占 1 字节，那么：

前 16 字节写入 `buf[0]` 到 `buf[15]`。
其余 4 字节写入紧接在 `buf` 高地址一侧的内存，超出了缓冲区边界。

图中上方是高地址，下方是低地址，箭头表示本次输入数据的连续写入方向。

在这个假设布局中，越界的 4 字节覆盖了相邻区域，尚未到达保存返回地址的位置。图中的中间区域仅用于说明位置关系，实际内容和大小需要通过反汇编与调试确认。

### 越界写入怎样影响返回地址

在普通的 x86-64 函数调用中，`call` 指令会把它后一条指令的地址压入栈中，作为返回地址。被调用函数正常返回后，程序便可以从这个地址继续执行。

对于图示布局，保存的返回地址位于 `buf` 的高地址方向。如果越界写入的范围延伸到这个位置，就可能改写返回地址的部分或全部字节。

这里需要区分：

**缓冲区大小**：`buf` 本身占用的 16 字节。
**返回地址覆盖偏移**：从 `buf` 起始地址到保存返回地址位置的字节距离。

两者之间可能存在对齐填充、保存的栈帧信息或 Canary。因此，仅凭 `char buf[16]`，无法确定覆盖返回地址所需的偏移。

### 被改写的返回地址怎样影响执行流程

函数准备返回时，通常会先恢复栈指针，使 `rsp` 指向保存的返回地址。

对于本文讨论的普通 64 位近返回，`ret` 将栈顶的 8 字节作为返回目标；在返回成功的情况下，处理器从该目标地址继续执行。

如果 `rsp` 指向的这 8 字节已经被改写，`ret` 尝试使用的返回目标就可能发生变化。

不过，改写返回地址只是影响控制流的一个条件。程序还需要能够执行到 `ret`，通过相关保护检查，并且目标地址满足执行条件。无效的目标地址、不可执行的内存或保护检查失败，都可能导致程序终止。

## 利用栈溢出的基本思路与条件

栈溢出造成的内存破坏能否被利用，取决于能够改写哪些数据，以及这些改写会怎样影响程序。下面继续以覆盖保存的返回地址、改变函数返回后的执行位置为例，说明需要确认的条件。

### 明确写入范围和覆盖目标

首先找到输入点，确认数据从哪里开始写入、最多能够写入多少字节，以及输入和拷贝过程中是否存在截断或字符过滤。这些因素决定了实际能够控制的内存范围和内容。

随后结合反汇编与调试，定位保存返回地址的位置，确定它与输入起始位置之间的字节距离，也就是覆盖偏移。发送数据的长度、实际写入的长度和覆盖偏移分别表示不同的量，需要在分析时区分清楚。

例如，前面的 `read(0, buf, 64)` 只给出了最大读取长度。它实际读入多少字节、这些字节覆盖到什么位置，仍需结合运行结果确认。

### 构造输入并满足执行条件

明确覆盖目标后，还需要确定希望程序转向的代码及其入口地址。为触发漏洞并实现预期效果而专门构造的输入，通常称为 payload。

在最简单的返回地址覆盖场景中，payload 可以由填充数据和编码后的目标地址组成。填充数据使后续字节到达保存返回地址的位置，目标地址则用于改变返回目标。实际构造时，需要考虑地址的宽度、字节序和输入长度限制。

转向某个函数时，还要满足它的调用条件，例如参数的位置与取值、栈对齐，以及函数执行结束后的返回安排。通过 `ret` 进入函数时，这些状态需要由已有程序状态和构造的数据共同满足。仅仅到达函数入口，还不能说明目标操作已经成功完成。

### 结合保护机制和调试结果验证

程序的编译选项和运行环境会影响上述过程，常见机制包括：

| 机制 | 主要作用及其影响 | 参考资料 |
| --- | --- | --- |
| Canary | 在受保护函数中加入栈保护值及检查代码。检查失败时程序会终止，可能在执行返回指令前中止利用。 
| NX | 禁止执行被标记为不可执行的内存中的指令。如果栈不可执行，直接执行放在栈上的 shellcode 就会受到限制。
| ASLR | 随机化栈、共享库等区域的地址，影响目标地址的确定和利用的稳定性。
| PIE | 使主程序能够以不同基址装载；配合 ASLR 后，主程序代码的运行时地址也可能变化。 

这些机制影响的环节不同。Canary 可能在函数返回前检测到覆盖；NX 限制内存的执行权限；ASLR 与 PIE 则影响地址是否稳定。

调试时，应核对实际写入范围、保存的返回地址是否按预期改变，以及程序最终执行到了哪里。程序崩溃只能说明出现了异常，具体原因还需要结合触发异常的指令和当时的运行状态判断。

## 怎样修复这个越界写入

保护机制会影响漏洞的利用条件，程序本身仍应确保写入范围不超过缓冲区容量。对于前面的示例，可以将读取长度限制为缓冲区的实际大小：

```c
#include <stdio.h>
#include <unistd.h>
void safe(void)
{
    char buf[16];
    ssize_t n = read(0, buf, sizeof buf);
    if (n < 0)
    {
        perror("read");
        return;
    }
}
```

这里将最大读取长度限制为 `sizeof buf`，使一次读取最多向缓冲区写入 16 字节，避免原示例中读取长度超过缓冲区容量的问题。使用 `sizeof buf`，也能让这里的读取上限随数组大小一起调整。

`read()` 的返回值表示实际读入的字节数，后续处理应以这个长度为准。返回 `0` 表示读到了输入末尾；返回 `-1` 表示发生错误，示例中使用 `perror()` 输出错误信息后返回。

另外，`read()` 不会自动补上字符串结尾的 `'\0'`。如果后续要把输入作为 C 字符串使用，应将读取上限设为 `sizeof buf - 1`，并在确认返回值非负后执行 `buf[n] = '\0'`。

## 常见利用思路

在已经能够影响函数返回路径的前提下，可以按后续执行的代码来自哪里，理解代码注入与代码复用这两种思路。下面再结合它们的执行目标和组织方式，介绍常见术语。

### 代码注入：执行写入内存的机器代码

代码注入的思路，是通过可控输入将机器代码写入进程内存，再将执行流程转向这段代码。

这类为完成特定操作而构造的机器代码通常称为 shellcode；通过覆盖返回地址转向它的做法常称为 ret2shellcode。

这种方式要求机器代码能够按预期写入、入口地址能够确定，并且所在内存区域允许执行。分析时，需要同时考虑代码的存放位置、输入限制和内存执行权限。

### 代码复用：执行进程中已有的代码

代码复用利用的是程序自身或已加载库中的现有代码。可以从复用已有函数和组合短指令片段两个角度理解。

#### 复用已有函数

ret2win 的目标是执行程序中已有的、能够完成预期操作的函数。CTF 题目中，这类函数可能负责打印 flag 或执行题目预设的成功逻辑；它的名字不一定是 `win()`。利用时需要确认函数入口、参数及其他执行条件。

ret2libc 则以 libc（C 运行库）中已有的函数为执行目标。分析重点包括所用函数的入口、参数和调用后的执行安排；直接返回到某个 libc 函数时，还需要确定它的运行时地址。

这两个名称主要说明目标函数的位置或用途。具体怎样准备参数、怎样组织后续执行，还需要结合程序架构和可用代码分析。

#### 组合已有的短指令片段

ROP（Return-Oriented Programming，面向返回编程）的常见用法，是利用程序或已加载库中的短指令片段来组合操作。在 x86-64 中，这些片段通常以 `ret` 结尾，常称为 gadget。

通过安排栈上的地址和数据，可以组织这些片段的执行顺序，完成设置寄存器、准备参数、调用函数等操作。它复用的是已经存在的可执行代码，因此可以在栈不可执行的情况下使用；实际能否成功，还取决于可用片段、运行时地址和其他保护条件。

这些做法可以出现在同一次利用中。例如，先用 ROP 片段设置参数，再转向 libc 函数，就同时涉及 ROP 和 ret2libc。
