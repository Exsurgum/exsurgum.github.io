## 什么是 Shellcode

本文中的 **Shellcode** 指的是一段独立、位置无关、可以直接交由 CPU 执行的机器码片段。早期的攻击场景常把这段代码用来启动一个交互式 Shell（例如调用 `execve("/bin/sh", ...)`），因此得名；在现代二进制安全与 CTF 语境里，它也泛指任何注入到目标进程内存中执行的自定义机器指令，比如只做文件读写的短指令序列。

在漏洞利用分类上，Shellcode 属于**代码注入（Code Injection）**，与 [01.0 栈溢出概述](/posts/stack-overflow/) 中提到的 `ret2libc`、ROP 等**代码复用（Code Reuse）**相对：

- **代码注入**：自己把机器码写进可读写且可执行的内存，再劫持控制流跳过去执行。
- **代码复用**：在内存不可执行（NX 开启）时，不注入新指令，而是拼凑程序或库里已有的代码片段（gadget）完成目标。

两者的前提边界很清楚：只要目标内存区域同时具备**可写（W）**和**可执行（X）**权限，且控制流能跳转到写入位置，代码注入就能成立；一旦系统严格执行 `W^X`（写与执行互斥），纯 Shellcode 注入就会被直接挡住。

## 为什么普通编译出的代码不能直接用

新手常有一个疑问：用 C 写一段调用 `execve` 的程序，编译后把 `.text` 段的机器码抠出来，算不算 Shellcode？通常不行，原因有三点：

1. **依赖加载器与动态链接**：普通可执行文件调用库函数时，走的是 PLT/GOT 表和动态链接器重定位。一段裸机器码被塞进栈或堆里执行时，没有任何加载器帮它修地址，直接调外部函数地址几乎必崩。
2. **依赖绝对地址**：普通程序里的字符串常量（如 `"/bin/sh"`）放在 `.rodata` 段，指令通过固定虚拟地址或编译期算好的偏移去取。注入后的代码落在哪块地址往往不固定，写死地址就找不到数据。
3. **包含截断字符**：编译器生成的正常指令里充斥着 `0x00`（空字节）等数值，遇到按 C 字符串处理输入的函数时，还没写完就被截断了。

因此，能在漏洞场景中稳定运行的 Shellcode 必须同时满足两个核心要求：**直接通过系统调用（syscall）和内核交互**，以及**自身完全位置无关（PIC）**。

## 核心原理与系统调用机制

### x86-64 Linux 系统调用约定

绕过 libc 的库函数封装后，用户态代码直接通过 `syscall` 指令向内核请求服务。以 x86-64 Linux 为例，系统调用的参数传递与普通 C 函数调用有明显区别：

| 角色 | 普通函数调用（System V ABI） | Linux `syscall` 约定 |
| --- | --- | --- |
| 调用号 / 返回值 | 返回值在 `rax` | 调用号放 `rax`，返回值回 `rax` |
| 第 1\~3 个参数 | `rdi`、`rsi`、`rdx` | `rdi`、`rsi`、`rdx` |
| 第 4 个参数 | `rcx` | **`r10`**（`rcx` 用于保存返回地址） |
| 第 5\~6 个参数 | `r8`、`r9` | `r8`、`r9` |

有一点很容易漏掉：执行 `syscall` 时，CPU 硬件会把下一条指令地址存进 `rcx`，把 `rflags` 存进 `r11`。因此 `syscall` 返回后，`rcx` 和 `r11` 的原值会被破坏，不能指望它们在系统调用前后保持不变。

常见基础系统调用的号（x86-64 下定义在 `<asm/unistd_64.h>`）如下：

- `sys_read`（`0`）：从文件描述符读取数据。
- `sys_write`（`1`）：向文件描述符输出数据。
- `sys_open`（`2`）：打开指定路径的文件。
- `sys_execve`（`59`）：用新程序替换当前进程映像。
- `sys_exit`（`60`）：正常结束当前进程。

在 C 语言里，不经过包装函数直接发起系统调用，等价于下面这种形态：

```c
#include <sys/syscall.h>
#include <unistd.h>

// 对应寄存器约定：rax = 59, rdi = "/bin/sh", rsi = 0, rdx = 0
syscall(SYS_execve, "/bin/sh", NULL, NULL);
```

### 数据怎么做到位置无关

既然不能写死 `.rodata` 的绝对地址，Shellcode 里的字符串和结构体就得“随身携带”，常见有两种组织方式：

1. **压栈构造再取 `rsp`**：把需要的短字符串（比如 `"/bin/sh\x00"`，正好 8 字节）作为立即数或通过寄存器运算放进栈顶，此时 `rsp` 指向的位置就是该字符串的首地址，直接 `mov rdi, rsp` 即可传参。
2. **`rip` 相对寻址**：把字符串附在指令流末尾，在 x86-64 下利用 `lea rdi, [rip + offset]` 直接算出运行时地址；或者用 `jmp`/`call` 配合在栈上压入返回地址的技巧定位紧随其后的数据区。

这两种方式都不依赖固定装载基址，无论这段代码被写到栈上哪一页、堆里哪一块，都能自己定位到自带的数据。

## 编码限制：坏字符与长度约束

即使系统允许某块内存执行代码，输入通道本身往往还有格式限制。

### 什么是坏字符（Bad Bytes）

很多输入函数并不会老老实实把所有字节原样读进去，它们遇到特定字节就会停下或报错：

- **空字节 `\x00`**：`strcpy`、`strcat`、`sprintf`、`scanf("%s")` 等 C 字符串函数把 `\x00` 当作结束符，后面的字节全部丢弃。
- **换行与空白符（`\n`、`0x0a`、`\r`、`0x0d`、`0x20` 等）**：`gets`、`fgets`、`scanf` 会按行或空白分隔符截断输入。

正常汇编里很容易产生 `\x00`。比如：

- `mov rsi, 0` 在机器码里需要编码一个 32 位或 64 位的全零立即数，会带出一串 `00`。
- `mov rax, 59` 会把 59 编码成 4 字节小端序 `3b 00 00 00`，同样带着 3 个 `00`。
- `push` 一个含零字节的 64 位地址或字符串常量时，立即数本身也会夹带 `00`。

为了避开坏字符，底层编码上通常会做等价替换：

- **清零用异或或相减**：`xor esi, esi` 既把 64 位寄存器 `rsi` 高低全清零（32 位写操作会自动零扩展到 64 位），机器码又短，还不带 `\x00`。
- **小常数用低位寄存器写**：先清空 `rax`，再给低 8 位赋值（例如写 `al = 59`），避免 32 位立即数的高位补零。
- **常量做算术变换**：如果字符串或常量本身含 `\x00`（如结束符），可先压入非零值再通过位运算或加减在寄存器里还原。

### 空间限制与分段加载

有些漏洞给的缓冲区很小（例如只能写二十多字节），放不下完整的功能逻辑。常见思路是把流程拆成两段（Staged）：第一段只放极短的“引导读入代码”（例如只调一次 `sys_read` 往当前可写可执行区域读入更大的一块数据），第二段再把完整逻辑读进来接着执行。

## 常见防护机制与缓解思路

现代操作系统默认打开多层缓解措施，专门用来压缩 Shellcode 的生存空间。

| 机制 | 作用位置 | 对 Shellcode 的影响 |
| --- | --- | --- |
| **NX / DEP（`W^X`）** | 内存页表权限位 | 栈、堆等数据页标记为不可执行；只要跳过去执行，CPU 立刻触发段错误（SIGSEGV）。 |
| **ASLR / PIE** | 进程虚拟地址空间 | 栈、堆、`mmap` 区域和主程序基址每次启动随机化，不知道写入位置就无法直接跳过去。 |
| **Seccomp（`seccomp-bpf`）** | 内核系统调用入口 | 按规则过滤进程能调用的 `syscall` 号；禁用 `execve`/`execveat` 后，拉起 Shell 的思路直接失效。 |
| **SMEP / SMAP** | CPU 内核态控制位 | 防止内核态代码直接执行或直接读写用户态内存页，限制内核漏洞向用户态 Shellcode 借力。 |

### NX 与 `-z execstack`

GCC 编译出的 Linux 程序默认开启栈不可执行（NX）。用 `readelf -l` 查看程序头时，`GNU_STACK` 段的标志通常是 `RW`（可读可写）。只有显式加上 `-z execstack` 编译，或者程序历史代码里用到 GCC 嵌套函数 Trampoline 时，`GNU_STACK` 才会变成 `RWE`，让栈重获执行权限。

在部分题目或特殊场景里，即便默认开启了 NX，如果程序自己通过 `mmap` 申请了 `PROT_READ | PROT_WRITE | PROT_EXEC`（即 `RWX`）内存，或者存在未做权限约束的 `mprotect` 调用路径，依然会留出可执行窗口。

### Seccomp 与 ORW 限制

在启用 `seccomp` 沙箱的题目或容器环境中，开发者经常禁用 `execve`（59）和 `execveat`（322），让“开 Shell”这条路走不通。如果此时沙箱仍放行了文件与 I/O 相关的系统调用，攻击面就会从“拿 Shell”退化为 **ORW（Open - Read - Write）**：依次调用 `open` 打开目标文件、`read` 读入内存、`write` 输出到标准输出。

反过来，从防御角度看，配置 `seccomp` 白名单时只放行服务真正必需的系统调用和参数条件（例如禁止打开任意新文件或禁止创建子进程），能大幅降低内存破坏漏洞被利用后的危害上限。

## 怎样在开发中防范代码注入

1. **修复根源漏洞**：参考 [01.0 栈溢出概述](/posts/stack-overflow/) 和 [03.0 格式化字符串漏洞概述](/posts/format-string/)，从源头校验输入边界与格式串，不给劫持控制流的机会。
2. **坚持 `W^X` 原则**：编译阶段不关闭栈保护和 NX（避免使用 `-z execstack`）；动态生成代码（如 JIT）时，先以 `RW` 写入，完成后用 `mprotect` 切换为 `R-X`，不要让同一页长期同时持有 `W` 和 `X` 权限。
3. **收窄进程权限**：对解析外部复杂输入的服务启用 `seccomp` 白名单，禁用 `execve`、`fork` 等高危系统调用，配合 `-fPIE -pie -Wl,-z,relro,-z,now` 提高整体利用门槛。

`pwntools` 常用工具（`asm`/`disasm`/`shellcraft`）和基础汇编写法见下一篇：[02.1 Pwn 中的 Shellcode 工具与基础汇编写法](/posts/shellcode-tools/)。
